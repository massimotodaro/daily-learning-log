## DL-2026-10-30-01 — Search the bug ledger for the failure code before diagnosing; the same refusal had five earlier records and one fix

**Areas:** Tools and workflow; Software engineering

**Tags:** `bug-ledger`, `debugging`, `permissions`, `agents`, `process`

### What I learned

A local start-up seed stopped with a closed refusal code meaning "this signed-in role has no grant for this route's
scope and purpose". The project's bug ledger already held five records of that exact code. Each had the same cause:
the route's permission was missing from the central list of grants the role registry projects onto user profiles.
Each had the same fix: add it there for the admitted roles and generate the database migration, keeping the route
strict. The build lane had not used that history, for two reasons. Its brief said to read only open bugs in its area,
while these five were all fixed. And the ledger was stale: hundreds of rows were unnumbered or still marked "fixed on
feature branch", so they were easy to skip.

The same build also repeated two other recorded bug classes from two weeks earlier. A grant refresh revoked a session
the seed had captured earlier, and a launcher dropped a child process's failure reason.

### What I did

I refreshed the ledger, then read every lesson and every ledger row, plus each record that matched the failure. I put
the five records and their common fix into the next fix brief. That round found and fixed all five missing grants in
one pass on a held stack, instead of one per full restart. I also made "read every lesson and every bug record, then
confirm before starting" a standing first step for every build.

### Evidence or example

The five earlier records had the same symptom, cause and fix. The round that was given them identified five missing
grants and closed them together. The rounds before it had advanced one failure per full restart.

### Why it matters

A ledger pays off only when someone searches it with the failure in hand. A ledger read only for its open items
misses the fixed bugs, and those hold the answer most often. Searching by the exact reason code turns diagnosis into
a lookup.

### Open questions

Should a failing run automatically search the ledger for its closed reason code and print the matching records?

### Next step

Before diagnosing any closed failure code, search every bug record for it, open and fixed alike, and start from the
recorded fix.
