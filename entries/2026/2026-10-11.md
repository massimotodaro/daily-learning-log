## DL-2026-10-11-01 — Rehearse an upgrade of a long-lived database on a copy, and snapshot it first

**Areas:** Software engineering; Tools and workflow

**Tags:** `migration`, `databases`, `ci`, `testing`, `operations`

### What I learned

A shared development environment went down for about eighteen hours after its database was migrated in place to
catch up with the main branch. The automated checks that had approved every change along the way all ran against
freshly created, empty databases, so none of them had ever proven that an *upgrade of an existing database holding
real data* would succeed. Once the live service was stopped and the migration started, each blocker that surfaced
only became visible after the previous one was fixed — a legacy record missing a field the new schema required,
then a derived value nothing had back-filled, then a dependent check that assumed the new shape already existed.
Because the migrations were forward-only, there was no way back once started, and because no snapshot had been
taken first, the only way out was forward, one blocker at a time.

### What I did

Confirmed from the incident timeline that every CI shard provisions a disposable, empty database per run, so green
CI had never once exercised an in-place upgrade of aged data. Captured the rule going forward: before any restart
that will migrate a long-lived database, take a full snapshot of it; then rehearse the exact migration against a
restored copy of that snapshot in a disposable environment; only once that rehearsal is clean, stop the live
service and run the real migration. Also noted that this rehearsal should become a standing automated check —
migrating a realistic aged snapshot to the latest schema — run whenever a migration is proposed, not just when
someone remembers to do it by hand.

### Evidence or example

Incident log: service unavailable from one evening until partway through the next day; the first database snapshot
of the recovery was taken only after the outage was already hours old, not before the migration began. Each
restart attempt surfaced a new, previously invisible blocker rather than succeeding outright.

### Why it matters

"CI is green" proves the code is correct against a clean database; it says nothing about whether that code can
safely take an existing, aged database from its current state to the new one. Those are different claims, and
conflating them turns a routine upgrade into an open-ended incident, because forward-only migrations give you no
rollback once you have started and no snapshot means no restore.

### Open questions

How much aged, realistic test data is "enough" for an upgrade-rehearsal check to be trustworthy, short of a full
production-scale copy?

### Next step

Add an automated check that migrates a retained, realistic snapshot of aged data to the latest schema on every
migration change, so the rehearsal happens by default rather than by memory.

### Sources

Own incident review of a local development environment outage, 2026-10-11.
