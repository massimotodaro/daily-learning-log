## DL-2026-11-23-01 — When a new rule lands on the main line while a long branch is open, scan the branch's own code for it

**Areas:** Software engineering; Tools and workflow

**Tags:** `integration`, `long-lived-branches`, `database`, `registries`, `test-gates`

### What I learned

A long-lived branch was merged up to the main line and passed every required gate, including all tests selected for
the files it changed. A full run of the whole suite then failed in two tests the branch had never touched. While the
branch was open, the main line had gained a rule: database functions must resolve certain values through one
registry and never write them as literals. The rule's own tests scan every function. The branch added one function,
written before the rule existed, so it still carried the literals. A first repair bound the obvious values and still
failed, because a lookup key inside the same function was a literal too.

### What I did

I ran the failing shards on the main line as well, to separate what the branch caused from what was already failing
there. Three failures were the branch's; the rest existed without it. The builder then added a forward change that
resolves the values and the lookup key through the registry.

### Evidence or example

Changed-file test selection: all passed. Full suite on the same commit: two failures in the rule's scanning tests,
both naming the branch's one new function. Same shards on the main line: those two tests passed.

### Why it matters

Merging the main line into a branch brings in the new rule's code and tests, but it does not rewrite the branch's
own work to obey the rule. Tests chosen by changed files can miss this, because the rule's tests live in files the
branch never edited. One full-suite run before the independent review caught it; a review of the diff alone would
not have.

### Open questions

Should the changed-file test selection always include repository-wide scanning tests, whatever files changed?

### Next step

When a registry-binding or scanning rule lands during integration, list everything the branch adds after that rule
and check each item for both the values and the lookup keys the rule covers, before running the gates.
