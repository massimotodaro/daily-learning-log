## DL-2026-10-02-01 — Porting a guard to a second agent harness: be at least as lenient as the harness, and judge the change from the base

**Areas:** AI and agent systems; Security and privacy; Tools and workflow

**Tags:** `agent-harness`, `hooks`, `guardrails`, `ci`, `parsing`

### What I learned

A workflow guard written for one coding-agent harness can be moved to another without forking its logic: keep one
implementation, and put a thin adapter in front of it that translates the second harness's hook input into the shape the
guard already understands. The hard part is not the translation but the ways a guard quietly lets things through:

- **Parse no more strictly than the tool does.** The guard read patch headers only at column 0; the harness trimmed
  whitespace first. A harmless path followed by an indented code path slipped past. The same happened with escaped
  characters in shell text, and with a `..` spelling of a protected file path that the guard resolved for its decision
  but passed unresolved to the judge.
- **Gate the effect, not the tool name.** The same patch engine was reachable from a shell alias, so the shell route had
  to be judged with the same parser.
- **The host's failure mode is part of the design.** This harness lets a tool call through when a hook crashes or times
  out, so the adapter turns every crash into a refusal and arms its own watchdog to refuse before the host's deadline.
- **A server-side check must not take its definition from the change it judges.** A CI check triggered by the
  change's own workflow file can be rewritten by that change. It has to run the base branch's copy and only read the
  head with git. A path-classifying diff must also disable rename detection, or moving code into an "allowed" folder
  hides the removal.
- **A proof run proves presence, not absence.** "No refusal appeared" is not proof that the allowed step worked; each
  proof needs the right success, in the right order, by the right actor.

### What I did

Built a generator that derives the second harness's skills, agent definitions and hook registration from the
untouched source kit, with a drift test; an adapter for the two existing gates; a pull-request check; and a real pilot
run in a throwaway clone. Every step went through an adversarial review loop, which found and closed five real bypasses.

### Evidence or example

Each bypass was reproduced against the real harness binary before it was fixed, then pinned with a test that goes red
when the guard is disabled. The final pilot recorded the harness's own refusal text for an off-plan edit, an
out-of-order step and an unfinished plan, and restored the user's harness config byte for byte.

### Why it matters

Moving work between agent vendors to share cost is only safe if the guard rails move with it. Most of the risk sat in
the gap between "the guard's idea of the input" and "the tool's idea of the input", which no amount of reading the guard
alone would show.

### Open questions

Whether finished subagent threads count towards the second harness's concurrency cap, and whether the server-side check
result attaches to the change's head commit the way the branch protection expects.

### Next step
