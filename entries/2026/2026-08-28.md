## DL-2026-08-28-01 — Stable machine states need clear human-facing language

**Areas:** AI and agent systems; Product and design

**Tags:** `state-models`, `terminology`, `human-oversight`

### What I learned

An internal machine state and the language shown to a school user serve different
purposes. Machine vocabulary should remain stable for compatibility and evidence, while
the interface should translate it into language that the responsible human can understand
and act on.

### What I did

I worked on an AI inference and safeguarding assessment, strengthened the human review
legend, and defined school-facing categories for non-green model inputs. I retained the
underlying protocol states while making their presentation clearer for an authorised
safeguarding lead.

I added tests proving that each applicable internal state maps to exactly one
human-facing category and that an ordinary green state maps to none.

### Evidence or example

Verified Git history records the inference-assessment surface, explicit review options,
review-legend reconciliation, the state-to-label mapping, and focused mapping tests. This
retrospective omits private assessment records, provider identifiers, learner-like test
content, and internal repository links.

### Why it matters

Stable protocol values prevent integration drift. Clear human-facing labels reduce
ambiguity for the people responsible for acting on the result. Preserving both avoids
forcing implementation terminology into a sensitive operational workflow.

### Open questions

- How should future protocol states be admitted without silently changing school-facing
  language?
- Which human roles should approve changes to safeguarding terminology?

### Next step

Keep the internal-to-human vocabulary mapping explicit, exhaustive, and covered by tests
whenever a new model state is introduced.

## DL-2026-08-28-02 — Blocking unsafe output is not proof of human delivery

**Areas:** Security and privacy; Education and domain knowledge

**Tags:** `safeguarding`, `audit`, `human-handoff`

### What I learned

Detecting or blocking a concerning input is not proof that a human safeguarding workflow
received it. A system may correctly stop generation yet still fail operationally if it
does not create the required authorised, auditable handoff.

### What I did

I documented the requirement that every non-green state must produce a distinguishable,
local safeguarding item. I separated three events that are easy to conflate:

1. the model classified an input;
2. the application prevented an unsafe response; and
3. the responsible human received an actionable item.

Only the third establishes the operational handoff.

### Evidence or example

The day's verified work recorded that audit-only blocking was insufficient evidence of
delivery. The runtime must create the authorised handoff and its audit evidence before it
claims that the responsible human received the item.

### Why it matters

Trustworthy safeguarding depends on causal delivery, not merely classification or UI
copy. The system must persist the handoff, retain the distinction between categories, and
make delivery failure visible without exposing sensitive content.

### Open questions

- How should delivery be monitored without exposing sensitive content outside its
  authorised boundary?
- Which service-level target should apply between classification and human visibility?
- How should the interface communicate degraded delivery without implying that an
  external referral happened automatically?

### Next step

Trace the complete causal path from non-green classification to the authorised human
queue, including persistence, audit evidence, failure handling, and visible delivery
state.
