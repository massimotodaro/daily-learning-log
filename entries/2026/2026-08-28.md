## What I learned

An internal machine state and the language shown to a school user serve different
purposes. Machine vocabulary should remain stable for compatibility and evidence, while
the interface should translate it into language that the responsible human can act on.

I also learned that detecting or blocking a concerning input is not proof that a human
safeguarding workflow received it. A system may correctly stop generation yet still fail
operationally if it does not create the required authorised, auditable handoff.

## What I did

I worked on an AI inference and safeguarding assessment, strengthened the human review
legend, and defined school-facing categories for non-green model inputs. I kept the
underlying protocol states stable while making their presentation clearer for an
authorised safeguarding lead.

I documented the requirement that every non-green state must produce a distinguishable,
local safeguarding item. I also added tests proving that each applicable internal state
maps to exactly one human-facing category and that an ordinary green state creates none.

## Why it matters

Clear labels help humans make consistent decisions, but trustworthy safeguarding requires
more than clear UI copy. The runtime must causally create the authorised handoff, retain
the distinction between categories, and produce audit evidence before claiming delivery.

This separates three ideas that are easy to conflate:

1. the model classified an input;
2. the application prevented an unsafe response; and
3. the responsible human actually received an actionable item.

Only the third establishes the operational handoff.
