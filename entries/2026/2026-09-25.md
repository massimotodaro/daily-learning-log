## DL-2026-09-25-01 — Record the reason code, not just the status

**Areas:** Cloud and delivery; Software engineering

**Tags:** `debugging`, `observability`, `error-handling`

### What I learned

An HTTP 403 has many possible causes. A test that records only the status discards the one field that would name the cause, and cleanup may then delete the database evidence too.

### What I did

Diagnosing a failed upload finalisation, I narrowed it using storage logs (the file had arrived; the server never checked it) and a surviving rate-limit row (the request had passed its first step), but could not name the check. The next goal made the test record the content-free reason code from every failed response; the cause turned out to be the test sending its own identifier instead of the one the server had reserved.

### Evidence or example

Once the reason code was captured, the fix took one run.

### Why it matters

Content-free reason codes are safe to log and turn guesswork into a lookup.

### Open questions

- Which other harnesses throw away response detail on failure?

### Next step

Make every test harness include the server's reason code in its failure message.

## DL-2026-09-25-02 — A cloud email sandbox checks the recipient too; simulation is not a real send

**Areas:** Cloud and delivery; Security and privacy

**Tags:** `email`, `least-privilege`, `verification`

### What I learned

In a managed email service's sandbox, a send is authorised against the recipient's verified identity as well as the sender's. A least-privilege policy written for the sender's domain alone fails once sender and recipient are on different domains.

### What I did

After moving the sender to a new domain, a policy simulation passed, but real sends failed with access denied. One real send proved the cause; the policy gained exactly the recipient identity, and a real email arrived four seconds later.

### Evidence or example

The same review showed the account's production-access request had been denied, meaning no real customer inbox could receive mail; sending was moved to an EU transactional-email provider, with a resubmission kept as a fallback.

### Why it matters

A permission simulator only answers the question you ask it. A real send is the proof.

### Open questions

- How should delivery to real customer domains be proven before launch without using customer data?

### Next step

Require one real, content-free delivery proof after any change to a sending path.

## DL-2026-09-25-03 — Processed or rejected, never 'accepted with a note'

**Areas:** Product and design; Education and domain knowledge

**Tags:** `content-pipeline`, `accessibility`, `readability`

### What I learned

If an organisation is responsible for what enters its content library, every item must pass through one processor that enforces all mandatory rules, or it does not enter. Warning the author and accepting anyway moves the responsibility to the wrong person.

### What I did

I recorded one processor for all content, whether uploaded or written with the assistant: it converts documents into a structured page-of-blocks format, applies layout and readability rules per age band and screen size, simplifies wording above the target reading level while keeping verbatim sources word for word, and shows the teacher the result before it is accepted.

### Evidence or example

Research for the rules drew on WCAG 2.2 text presentation criteria, the British Dyslexia Association style guide, line-length studies and reading-age measures; a permissively licensed, offline document converter was chosen for a proof on five hard documents.

### Why it matters

Consistency and accessibility become properties of the system, not of each author's effort.

### Open questions

- How reliable are reading-level scores on short, subject-heavy text?

### Next step

Prove the converter on the hardest layout — an illustration with scattered labels — before replacing the current import.
