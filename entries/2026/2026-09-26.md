## DL-2026-09-26-01 — The prompt goes last: never put an instruction after the text someone will paste

**Areas:** AI and agent systems; Tools and workflow

**Tags:** `handover`, `sequencing`, `communication`

### What I learned

When a message hands someone a block to paste into another agent, they paste it the moment they see it. Anything
written below the block is read after the agent has already started, so a precondition placed there arrives too late.
Every precondition — a sign-in, a merge, an order between workers — belongs inside the handed-over task or in a
numbered step before the block, and a precondition the task already covers should not be repeated at all.

### What I did

I handed over a task and, underneath it, told the reader to sign in to a cloud account first because the session had
expired. The task itself already said to ask for that sign-in when needed. The reader pointed out that the instruction
was in the wrong place and redundant. The rule is now written into the project's agent instructions.

### Evidence or example

Message shape that failed: `[task block]` then "Before that, run the login". Shape that works: "1. Run the login.
2. Paste:" then `[task block]` as the last thing in the message — or nothing extra when the task already asks for it.

### Why it matters

Parallel agent work depends on the human router acting instantly on each handover. A misplaced instruction either stalls
a worker or is silently skipped.

### Open questions

- Could a message check flag any text that follows a paste block?

### Next step

Treat "is the paste block the last thing?" as a check before sending any handover.

## DL-2026-09-26-02 — Take a migration number at merge, and let shared environments receive only what is merged

**Areas:** Software engineering; Cloud and delivery

**Tags:** `database-migrations`, `ci`, `coordination`

### What I learned

When pull requests merge without first being brought up to date, a numbering check that runs inside one pull request
cannot see another open branch. Several branches can each pass while claiming the same migration number. And if one
branch's migrations are applied to a shared test environment before they merge, that environment's history forks from
the main branch: the drift check turns red, every later apply is refused, and a change the main branch needs never
reaches the environment.

### What I did

I enumerated every open branch's migration files against the main branch and against what the shared environment had
applied: four branches claimed overlapping numbers, and the environment was missing a main-branch migration that the
next end-to-end run would need. I allocated each migration a final number with a merge order, planned a guarded
one-transaction repair of the environment's history, and wrote a rule: the number is taken at merge (no auto-merge for a
pull request that adds a migration; re-check the main branch immediately before merging), and shared environments only
receive migrations that are already merged.

### Evidence or example

The daily drift check had been red for three days with "wrong name at version N" and "remote-only version N+1"; the
apply tool refused every change with a prefix mismatch.

### Why it matters

A migration is the one change that cannot be quietly undone once applied. Numbering by convention fails under parallel
work; it has to be allocated.

### Open questions

- Would a check that compares all open branches' migration numbers be worth its cost, or is the merge-time rule enough?

### Next step

Keep one allocation table and consult it before any task that adds a migration.

## DL-2026-09-26-03 — A support case closed for no reply is not a refusal

**Areas:** Business and leadership; Cloud and delivery

**Tags:** `vendor-management`, `verification`, `communication`

### What I learned

A provider's status field can say "denied" when the real history is that the provider asked a question, nobody
answered, and the case auto-closed. Read the correspondence, not only the status, before treating a request as refused
and changing plans around it.

### What I did

A production-access request had been recorded as denied, and a fallback provider had been chosen on that basis. Reading
the case correspondence showed the provider had asked for use-case detail eleven days earlier and then closed the case
for lack of a reply. The case was reopened and answered the same morning, with concrete examples of the messages sent;
the fallback continues as a backup rather than a replacement.

### Evidence or example

Correspondence order: request for information → reminder after 7 days → auto-close after 10 days with "we have not
heard back from you". None of it was a decision on the merits.

### Why it matters

Misreading a procedural closure as a refusal can trigger an unnecessary provider migration and its cost.

### Open questions

- How should provider support cases be tracked so an unanswered question is noticed within days?

### Next step

Record every open provider case with its last message and who owes the next reply.
