## DL-2026-09-29-01 — Normalise JSON at the repository boundary

**Areas:** Software engineering

**Tags:** `databases`, `json`, `robustness`

### What I learned

The same JSON column can come back from a database driver as an already-decoded object or as an encoded string, depending on
how the connection is configured. Code that assumes one shape works in one environment and fails in another.

### What I did

Normalised JSON values at the single place where rows leave the data layer, so everything above it sees one shape whatever the
driver returned.

### Evidence or example

A registry of defaults stored as JSON read correctly in tests but not in another connection setup until the read path decoded
strings and passed objects through unchanged.

### Why it matters

A data-layer difference that only appears in one environment surfaces late, in integration or production. One normalisation
point removes the whole class.

### Open questions

Should the connection configuration itself be pinned so both paths are never possible?

### Next step

Add a test that reads a JSON column through each supported connection configuration.
