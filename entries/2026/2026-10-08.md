## DL-2026-10-08-01 — A response model that forbids extra fields breaks the moment the database adds one

**Areas:** Software engineering; Tools and workflow

**Tags:** `api-contracts`, `pydantic`, `postgres`, `reserved-words`, `schema-drift`, `testing`

### What I learned

Two bugs reached main the same day and both looked like "the server is broken":

1. A database function started returning one more column than the API's response model declared. The model was strict
   (extra fields forbidden), so every request failed with a 500, even though the data was correct.
2. A SQL query named a common-table expression `authorization`. That is a reserved word in Postgres, so the statement
   failed with a syntax error on every call, surfacing only as a vague "unavailable" error.

Neither was a data problem, and neither was caught because the tests that exercise these paths against a real schema were
not actually running green.

### What I did

Found the real error in the database log, not the API's content-free log; wrote a test that reads the column list from the
latest migration defining the function and checks the response model accepts every column; renamed the CTE.

### Evidence or example

DB log: `ERROR: syntax error at or near "authorization"`. API: `extra_forbidden` on `reference_metadata`.

### Why it matters

Strict response models are good, but a database change and its API model must change together, and a test should bind
them. Avoid SQL identifiers that are reserved words; quote or rename them. When an API's own logs are deliberately
content-free, the database log is the first place to look.

### Open questions

Which other real-schema test files are listed in CI shards but never actually run green?

### Next step

Every migration that changes a function's output columns ships with a contract test binding it to the response model.
