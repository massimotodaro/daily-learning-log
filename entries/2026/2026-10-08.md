## DL-2026-10-08-01 — A response model that forbids extra fields breaks the moment the database adds one

**Areas:** Software engineering; Tools and workflow

**Tags:** `api-contracts`, `pydantic`, `postgres`, `reserved-words`, `schema-drift`, `testing`

### What I learned

Two bugs reached main the same day and both looked like "the server is broken":

1. A database function started returning one more column than the API's response model declared. The model was strict
   (extra fields forbidden), so every request failed with a 500, even though the data was correct.
2. A SQL query named a common-table expression `authorization`. That is a reserved word in Postgres, so the statement
   failed with a syntax error on every call, surfacing only as a vague "unavailable" error.

Neither was a data problem, and neither was caught because the tests that exercise these paths against a real schema were
not actually running green.

### What I did

Found the real error in the database log, not the API's content-free log; wrote a test that reads the column list from the
latest migration defining the function and checks the response model accepts every column; renamed the CTE.

### Evidence or example

DB log: `ERROR: syntax error at or near "authorization"`. API: `extra_forbidden` on `reference_metadata`.

### Why it matters

Strict response models are good, but a database change and its API model must change together, and a test should bind
them. Avoid SQL identifiers that are reserved words; quote or rename them. When an API's own logs are deliberately
content-free, the database log is the first place to look.

### Open questions

Which other real-schema test files are listed in CI shards but never actually run green?

### Next step

Every migration that changes a function's output columns ships with a contract test binding it to the response model.

## DL-2026-10-08-02 — Deployment automation that has never run against the real environment is untested, however green its tests

**Areas:** Tools and workflow; Software engineering

**Tags:** `deployment`, `ci`, `staging`, `postgres`, `gcp`, `oidc`

### What I learned

One staging-automation change was merged on unit tests alone and then failed five times in a row the first time it ran
for real: a resource name compared in the wrong form (project ID vs project number), a database host rule stricter than
the repo's own rule, the wrong audience format for Google's token exchange, a tool set up in the wrong job, and a role
change using attributes a non-superuser may not set on PostgreSQL 16+. Each failure stopped safely, but each cost a fix,
a review and a rerun.

### What I did

Fixed each defect in its own small pull request with a test, and reran after each merge.

### Evidence or example

Five consecutive failures of the same staging migration workflow, each before any data changed.

### Why it matters

Tests prove the code matches the author's assumptions; only a real run proves the assumptions. Automation that talks to
cloud providers and managed databases should get one real dry run before it is merged.

### Open questions

Can a dry-run against the real staging project be made a required step for deployment-automation changes?

### Next step

Add "one real staging dry run" to the definition of done for any deployment workflow change.

### Sources

Own staging work on DanteSchool, 2026-10-08.

## DL-2026-10-08-03 — A white screen on reload can be the browser running out of request resources, not the app

**Areas:** Tools and workflow; Software engineering

**Tags:** `vite`, `chromium`, `dev-server`, `http-cache`, `debugging`, `white-screen`

### What I learned

A large single-page app served by an unbundled dev server (one HTTP request per source module, 160–340 per page) went
white on the third or fourth full reload in the same Chromium tab. The app was not failing: Chromium refused to load
half its modules with `net::ERR_INSUFFICIENT_RESOURCES`, so the entry script never ran. Each reload re-validates every
cached module (`Cache-Control: no-cache` plus an ETag), and something in that path piles up per tab until the browser
refuses new loads. A new tab worked; the broken tab stayed broken.

### What I did

Reproduced it headlessly and counted failed requests per load (0, 0, 0, then 57). Ruled out, one at a time: the feature
branch (same failure on the main branch), sign-in (fails signed out too), requests left open across navigations (none),
cookies and header sizes (small), shared-memory space (free), headless-only behaviour (full Chromium fails too).
Turning the browser cache off made five of five loads clean. Then a dev-only server middleware that sends
`Cache-Control: no-store` and drops the conditional request headers, tested on a spare port: six of six loads clean,
signed in and out.

### Evidence or example

Signed-out reloads of the same tab: `failed 0, 0, 0, 57, 2`. With `no-store`: `0, 0, 0, 0, 0`.

### Why it matters

"White screen" names a symptom, not a cause. The first question is whether the app's own code even loaded: a list of
failed requests separates a browser or network refusal from a runtime error, an API error, CORS or authentication. A
diagnosis that skips that step ends up blaming the wrong layer.

### Open questions

Which Chromium limit is reached exactly; the net log did not record the refusal, so it happens before the network
stack.

### Next step

Make the dev-only `no-store` setting permanent in the dev server configuration so nobody has to rediscover it.

### Sources

Own diagnosis on a local development stack, 2026-10-08.
