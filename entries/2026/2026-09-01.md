## DL-2026-09-01-01 — Monitoring failures need root-and-cascade separation

**Areas:** Cloud and delivery; Tools and workflow

**Tags:** `ci`, `monitoring`, `release-provenance`, `failure-classification`

### What I learned

A red monitoring workflow can contain one causal failure followed by several cleanup and
artifact errors. Counting every red step as an independent incident creates noise and can
hide the first actionable defect.

Release provenance also needs to distinguish source history from runtime identity. When a
newer commit on the same main history is already deployed, an older scheduled checkout can
still verify it safely if the component fingerprint is exact. Unrelated history and a stale
fingerprint must continue to fail.

### What I did

I audited every retained failed run of a scheduled staging-assurance workflow, classified
the first failing step, separated primary failures from downstream cascades, and added
regressions for moving-main ancestry, absent-fixture cleanup, receipt handling, and schedule
overlap.

I kept the real stale-component signal red while removing false ancestry failures and
secondary errors that occurred before the browser test had run.

### Evidence or example

The audit inspected 1,217 failed logs. It separated 1,183 repository-contract false
failures from 34 genuine historical runtime, fixture, browser, or deployment failures.
Focused tests proved that same-history descendants with exact fingerprints pass, unrelated
history and stale fingerprints fail, pre-setup failures skip cleanup while attempted setup
without restoration metadata remains fail closed, and scheduled cadence exceeds the
workflow's maximum duration.

### Why it matters

Monitoring is useful only when a red result identifies real action. Preserving genuine
failure signals while removing deterministic cascades reduces alert fatigue without
turning the workflow into a cached or manufactured pass.

### Open questions

- Which monitoring surfaces should expose a primary-cause field separately from cleanup
  diagnostics?
- When should a genuine stale deployment alert automatically route to a deployment owner?

### Next step

Keep release checks based on exact component identity plus real source ancestry, and ensure
every scheduled job's cadence is longer than its bounded maximum duration.
