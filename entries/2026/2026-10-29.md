## DL-2026-10-29-01 — When you redact an error, keep its closed reason code; the prefix alone hides the cause

**Areas:** Software engineering; Tools and workflow

**Tags:** `error-handling`, `observability`, `redaction`, `debugging`, `local-stack`

### What I learned

A local start-up script runs a seed step in a child process. To make sure no secret ever reaches the log, it
turns the child's failure into a short, closed code. The design is good, but the reducer kept only the text
before the first colon. So the log said `seed_child_failed` and nothing more, even though the child's own code
was already safe to show (`seed_child_failed:session_revoked`). The redaction removed the one word that
explained the failure.

The cause was a single safe identifier that one layer had dropped. I spent three full cold starts of the stack
before I could see it.

### What I did

I didn't edit the script under test. I added a scratch hook outside the repository that wrapped the
child-process call and saved only the child's error-class lines to a private file. The next run showed
`RuntimeError: session_revoked`, which pointed straight at a session check in the product. The permanent fix,
assigned to the build, is for the reducer to keep the whole chain of closed codes.

### Evidence or example

Logged before: `SEED_FAILURE=seed_child_failed`, then `RUNTIME_FAILURE=unclassified_runtime_error`.
Hook output on the third run: `RuntimeError: session_revoked`, raised from the child's request-failure branch.

### Why it matters

Content-free error codes exist so that a failure can be named safely. A reducer that cuts the code chain throws
away the safe part along with the unsafe part, and every run after that is wasted. Redact values, never the
reason vocabulary.

### Open questions

Should every layer that reduces an error be tested on a nested failure, to prove the innermost closed code
reaches the log?

### Next step

When I review error-reduction code, check that a nested failure keeps its full chain of closed codes.

### Sources

Verified local evidence: the start-up runtime log and the output of the scratch diagnostic hook.

## DL-2026-10-29-02 — "Ready" is a claim about one moment: re-check liveness right before you hand a system to a checker

**Areas:** Tools and workflow; AI and agent systems

**Tags:** `readiness`, `agents`, `verification`, `local-stack`, `testing`

### What I learned

The start-up script printed its ready line once the servers answered. A background supervisor then carried on
seeding, failed, and took the whole stack down. My hold script had already recorded "ready" and kept holding a
stack that no longer existed. I handed it to an independent checker agent without looking again. The checker
spent its run finding that nothing was listening, and checked nothing.

A second gap sat behind the first. The seed passed its tests on a throwaway database, because those tests never
ran the supervisor's real sequence. On the real start-up path, a stored sign-in session was refused because the
product had invalidated it, and the seed died.

### What I did

I confirmed the checker's finding myself (no listeners, the failure lines in the runtime log), tore the stack
down and reproduced the failure on clean stacks, with nothing else signed in. The fix went back to the builder
with a precise brief and a pass condition based on liveness: the seed receipt is present, the follow-up step
completes, and the API stays healthy for two minutes afterwards.

### Evidence or example

Hold status: `ready`. Ports: nothing listening. The runtime log after the ready line: the seed failure line,
then the runtime failure line. The checker run used about 64k tokens and verified nothing.

### Why it matters

A green light only says what was true when it was printed. A check of a system that died after its green light
costs a full agent run and proves nothing. A seed tested only in isolation is not tested on the path that really
runs it.

### Open questions

Should the ready line be printed only after background seeding has finished, so it means ready to use and not
just started?

### Next step

Before delegating any check against a running system, probe its health endpoint in the same step that hands it
over. Make "stays healthy for N minutes after seeding" part of every cold-start pass condition.

### Sources

Verified local evidence: the hold-script status file, port listing, runtime log, and the checker's report.
