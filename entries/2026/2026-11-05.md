## DL-2026-11-05-01 — A reviewer's PASS without the required gate commands is not a pass

**Areas:** Tools and workflow; AI and agent systems

**Tags:** `ci`, `code-review`, `agents`, `quality-gates`, `process`

### What I learned

An agent reviewer passed every step of a backend build. The pull request then failed several required CI checks: a
literal-value scanner, a type checker run against a baseline, and a ratchet that rejects new tests that inspect source
instead of exercising behaviour. Nobody had told the reviewer to run those commands. "No blocking findings" only meant
"no findings in what I read".

### What I did

I added every required gate command to each reviewer brief and each step's pass list, and asked for one local script that
runs all of them the same way CI does.

### Evidence or example

The steps were coded in about 70 minutes and reviewed in about 2.5 hours. Merging took another 29 hours of red-gate
fixes: 37 ratchet findings, new type errors, literal-scanner hits and test-order failures, all found in CI after "PASS".

### Why it matters

A merge is decided by the required checks, not by the reviewer's opinion. A review that skips them moves the cost to the
slowest, most expensive loop: CI, one push at a time.

### Open questions

None.

### Next step

A reviewer's verdict states which gate commands it ran and their results. No commands means no PASS.

### Sources

Verified local evidence: the build's pull request checks and reviewer reports, 2026-11-02 to 2026-11-04.

## DL-2026-11-05-02 — Prove a hand-back where it will be reviewed

**Areas:** Cloud and delivery; Tools and workflow

**Tags:** `staging`, `deployment`, `verification`, `handover`

### What I learned

The build was proven on a fresh laptop stack, merged and deployed to staging. Its page then could not run on staging.
The staging deploy had never been given the restricted database logins the new code needs, and a ledger row recorded
that gap four days before the build started. The laptop proof created those logins itself, so it could not see the gap.

### What I did

I bound the four logins in the staging deploy, redeployed, and ran the seed there. I also proposed that the build's
first step checks the review environment and the final proof runs on it.

### Evidence or example

The page's data endpoint refused with a "database not configured" reason code on staging. After the logins were bound
and the service redeployed, the seed completed on staging.

### Why it matters

A proof on an environment the reviewer will never use only proves that environment. Gaps in deploy configuration show up
only where the configuration actually runs.

### Open questions

None.

### Next step

Before building, check the review environment's migrations, logins and open bugs. Finish by proving the hand-back on it.

### Sources

Verified local evidence: the staging service logs, deploy template and bug ledger, 2026-10-31 to 2026-11-05.

## DL-2026-11-05-03 — A seed must handle data that already exists, and ask when that data may be deliberate

**Areas:** Software engineering; Business and leadership

**Tags:** `seed-data`, `idempotency`, `data-migration`, `decisions`

### What I learned

The build's seed created records only when they were missing. Existing environments already held the same record under a
placeholder name: its code. The seed left that name in place, and CI caught it late. Simply overwriting would have been
wrong too, because a person may have renamed the record on purpose. The seed cannot tell a leftover from a choice, so the
rule is the owner's decision.

### What I did

I asked the owner. The ruling: the seed corrects a name only while it still equals the code, and keeps every other name.

### Evidence or example

A CI test failed on the code-named record. After the ruling the seed renamed only code-named records, and on staging it
left a deliberately named record unchanged.

### Why it matters

Seeds run against databases with history. "Create if missing" and "overwrite" are both policies about existing data, and
choosing between them can be a business decision.

### Open questions

None.

### Next step

A spec lists every case where the seed's data may already exist, and the owner decides each one before code is written.

### Sources

Verified local evidence: the build's CI run and the owner's recorded ruling, 2026-11-03.

## DL-2026-11-05-04 — Never use git stash in a repository with several worktrees

**Areas:** Tools and workflow

**Tags:** `git`, `worktrees`, `agents`, `parallel-work`

### What I learned

Git worktrees share one stash list. An agent in its own worktree ran a stash and then a pop. The pop applied another
session's stashed work: a database migration from a different build landed in the agent's tree.

### What I did

I recorded the rule: no `git stash` in multi-worktree repositories. Commit work in progress on the worktree's own branch
instead.

### Evidence or example

The bug ledger records the stray migration that the pop brought into the wrong worktree. `git stash list` shows the
same entries from every worktree of the repository.

### Why it matters

Parallel agents depend on strict isolation between worktrees. A shared, invisible stash breaks that isolation.

### Open questions

None.

### Next step

Agent briefs forbid `git stash`. Work in progress becomes a commit.

### Sources

Verified local evidence: the build's bug ledger and `git worktree` documentation (worktrees share `refs/stash`).

## DL-2026-11-05-05 — A hand-back states only values that were observed

**Areas:** Tools and workflow; AI and agent systems

**Tags:** `handover`, `verification`, `http`, `honesty`

### What I learned

The hand-back file promised one cache-control header value, copied from the route's code. The real response carried a
different value, because an app-wide security layer overwrote the route's header. The next consumer of a hand-back
builds on its claims, so an unobserved claim becomes their bug.

### What I did

I recorded the bug and made observation the rule: each claimed field, code or header names the real call that showed it.

### Evidence or example

A real response showed the app-wide value, not the promised one. The hand-back was corrected to the observed value.

### Why it matters

A hand-back is a contract. A claim inferred from reading the code is a guess, and the reader cannot tell it from a fact.

### Open questions

None.

### Next step

Every hand-back row is marked observed with its call, or marked not checked.

### Sources

Verified local evidence: the build's hand-back file and bug ledger, 2026-11-03.
