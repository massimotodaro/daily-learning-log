## DL-2026-11-11-01 — A green test gate covers only the files it lists; everything outside it rots silently

**Areas:** Software engineering; Tools and workflow

**Tags:** `testing`, `ci`, `test-gates`, `maintenance`

### What I learned

A required test gate split its tests into named shards, each listing directories or files. A full run of every shard
passed: more than thirteen thousand tests, no known failures. But a coverage check against the repository found that
about one test file in ten belonged to no shard. Nothing ran them, so nobody noticed when they stopped matching the
code. Almost half of those files failed. Most checked evidence from finished projects; a few belonged to tools still
in daily use. Builds that touched one of those tools inherited its failures and lost time diagnosing them.

### What I did

I listed every test file, subtracted the files any shard covers (respecting each shard's own exclusions), ran the
remainder one file at a time the way each is meant to run, and recorded one bug per failing file. Then I commissioned
one build to delete what nothing uses, fix what is kept and put every kept file inside a shard.

### Evidence or example

Full gate: every shard green. Outside the gate: 88 files, 47 failing when run individually. A first pass that loaded
them all in one process reported 37 extra load errors that were artefacts of the loading mode, not real failures.

### Why it matters

A green gate is a statement about its list, not about the repository. Untested code that still looks tested is worse
than code that is visibly untested, because it is trusted.

### Open questions

Should the gate itself fail when a test file exists that no shard covers?

### Next step

Make "every test file belongs to exactly one gate shard" a mechanical check, and run outside-gate files in the way
their own entry point expects before calling them broken.

### Sources

Verified local evidence: a full shard run and a per-file run of the uncovered files, 2026-11-11.

## DL-2026-11-11-02 — Target the service where the code runs in production, not the one its name suggests

**Areas:** Cloud and delivery; Software engineering

**Tags:** `deployment`, `specs`, `production`, `identity`

### What I learned

I wrote a build spec to give a production service a cloud identity and a safety-filter setting for one model route.
I chose the web API service because the route's code lived in the API package. The builder traced the callers and
found that, in production, the route is composed and run only by a background worker service, through a plug-in entry
point. The API had no production path to that model at all. Built as written, the change would have shipped, passed
its tests and fixed nothing.

### What I did

I verified the trace, corrected the spec to the worker's identity, template and deployment record, and restarted the
build. The owner then made "always write for production" a standing rule: every spec names the production service,
template and identity it changes, and proves the production path.

### Evidence or example

The route's module sat in the API package; the only production composer was in the worker package, loaded through an
entry point; the API's production gateway raised a deferred-activation error.

### Why it matters

Package layout says where code is written, not where it executes. A fix aimed at the wrong runtime is invisible until
the real path fails in production.

### Open questions

None.

### Next step

Before writing a deployment change, find the production composer of the code path (entry points, worker wiring,
runtime environment checks) and name that service in the spec.

### Sources

Verified local evidence: build hand-back and code trace, 2026-11-11.

## DL-2026-11-11-03 — A developer's cloud CLI sign-in can break unrelated tests; isolate ambient cloud config

**Areas:** Software engineering; Security and privacy

**Tags:** `testing`, `test-isolation`, `credentials`, `cloud-cli`

### What I learned

A cloud provider's newer CLI sign-in writes a session pointer into the default profile of the local configuration.
After the user signed out, the pointer stayed. From then on, creating any SDK client on that machine failed while
resolving credentials, even in tests that never call the cloud. One real-schema test that builds a client at start-up
failed for that reason alone, and looked like a product regression. The same sign-in had also been made as the
account's root user, which should never be used for daily work.

### What I did

I reproduced the client failure, showed it disappears when the local configuration is hidden, removed the stale
pointer, reran the test (it passed) and recorded a bug that the test reads the developer's ambient configuration.
The owner moved to a named administrator user with multi-factor authentication.

### Evidence or example

Client creation raised a "login session could not be loaded" error with the default configuration and succeeded with
the configuration file pointed at an empty file.

### Why it matters

Tests that read the developer's environment pass or fail by machine, not by code. Root sign-ins leave root sessions
behind in places other tools read.

### Open questions

None.

### Next step

Point tests at an empty cloud configuration unless they deliberately test credential resolution, and sign in with a
named least-privilege user, never the account root.

### Sources

Verified local evidence: test failure, reproduction and rerun, 2026-11-11.

## DL-2026-11-11-04 — Two git and access habits that cost time: looping over credential profiles, and amending a pushed commit

**Areas:** Tools and workflow; Security and privacy

**Tags:** `git`, `credentials`, `agents`, `process`

### What I learned

Two of my own errors in one day. First, when a read-only cloud call was refused for the intended identity, my command
looped over every local profile, including a root profile; its session had expired, so nothing ran, but the standing
rule is to stop on a refusal and report, never to try another account. Second, I amended a commit that was already
pushed; the branch diverged from its remote, and the force-push needed to fix it was blocked by the permission layer.

### What I did

I reported the profile loop plainly. For the branch, I soft-reset to the pushed commit and pushed the change as a new
commit, which needs no force.

### Evidence or example

A refused call, followed by an attempt under a second profile; a pushed commit amended, a rejected push, then a
soft reset and a normal push.

### Why it matters

A loop over credentials turns one refusal into an attempt to escalate. A rewritten pushed commit turns a one-line fix
into a history repair.

### Open questions

None.

### Next step

Name exactly one profile in every cloud command and stop on refusal. After a push, add commits; never amend.

### Sources

Verified local evidence, 2026-11-11.
