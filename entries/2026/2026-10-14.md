## DL-2026-10-14-01 — An exception pinned to a line number breaks on the next unrelated edit; and a change that skips its checkers ships the break

**Areas:** Software engineering; Tools and workflow

**Tags:** `static-analysis`, `allowlist`, `ci`, `code-review`, `agents`

### What I learned

A static check that forbids hard-coded values carried one approved exception, recorded by file, line number and a
fingerprint of the line. A later change, whose purpose had nothing to do with that value, added code higher up in the
same file. The approved line moved down, so the check now reported two failures at once: the exception was "stale"
(nothing at its recorded line) and the value was "new" (an unapproved literal at its new line). The value itself had
not changed at all.

Two things went wrong together. First, an exception keyed by position is fragile by design: any edit above it
invalidates it, so it punishes unrelated work and invites the lazy fix of re-pointing the exception to the new line.
Second, the change was pushed straight after the agent finished, without the two independent checkers that are meant
to verify every step before it lands. Both checkers, run afterwards, found the same break within minutes.

### What I did

Ran two independent checkers (different model vendors, separate clean copies of the repository) against the pushed
change. Both confirmed that the change's real purpose was correct and that it alone caused the two new red checks.
The fix was written to remove the cause, not to move the exception: read the value from the rule source that owns
it, delete the stale exception, and add no new allowance. The rule I took away: no step is pushed as finished until
its checkers have reported.

### Evidence or example

The check's own output was two findings for one value: "stale exception" at its old line and "unapproved literal"
forty lines further down, which is the same value seen at its old and new position. A sample
re-run of the affected tests on a fresh database also confirmed the change's actual goal: the error it targeted went
from 29 occurrences to 0, and no failure was new compared with the base branch.

### Why it matters

An exception should be bound to *what* is allowed, not *where* it currently sits; otherwise the allowlist decays
with every edit and the easiest "fix" is to re-point the exception, which slowly turns the check into rubber-stamping.
And a two-checker review only protects the main branch if it runs before the push, not after.

### Open questions

Can exceptions be keyed by symbol or by a content fingerprint alone, so that moving code never invalidates them,
without letting a changed value slip through under the old approval?

### Next step

Prefer removing an exception by moving the value to its owner; where an exception must stay, propose keying it by
content rather than line number.

### Sources

Verified local evidence: CI output of the failing checks, and the findings of the two independent checkers.
