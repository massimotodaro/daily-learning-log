## DL-2026-10-01-01 — Before retiring old tables, rehearse the drop in a rolled-back transaction

**Areas:** Software engineering; Tools and workflow

**Tags:** `migration`, `testing`, `databases`, `technical-debt`

### What I learned

A task said one component still depended on an old set of tables that another team was about to remove. The
description was out of date: the dependency had already gone in an earlier rewrite. So the useful deliverable was not a
code change but proof. Proof is cheap to get: run the real flow once for a baseline, then, inside one database
transaction that is always rolled back, drop the old tables and columns and replay the same events. If the output
matches row for row, the component is safe to cut over.

The rehearsal also shows what the removal will really break. A `drop ... cascade` silently takes every dependant with
it, including objects that belong to other teams. A test that trusts `cascade` hides that. The test has to list every
dependant first, fail on any it cannot classify, and hand the rest to their owners.

### What I did

- Checked the claim against the code and the live schema catalog, not against the task text.
- Wrote catalog guards against foreign keys, dependencies, row-level policies, function bodies and imports. Each guard
  was proved able to fail with a rolled-back probe.
- Wrote the drop-and-replay test. It found three objects owned by other teams that the removal must rewrite, not drop.

### Evidence or example

```sql
begin;
  -- list every object depending on the old tables or column, in any schema; fail if one cannot be placed
  drop table old_scores, old_policies cascade;
  alter table assignments drop column old_mode;
  -- replay the award events; compare the new rows with the baseline
rollback;
```

An adversarial reviewer found the first version of the dependency query skipped row-level policies: it could not place
them in a schema, so it filtered them out. Failing closed on unplaced rows fixed it.

### Why it matters

Retiring old schema is where silent breakage hides: whoever drops the tables rarely owns every reader. A rehearsal in a
rolled-back transaction gives the team that drops the tables a list of everything the drop will break, and gives each
reader proof that its own results won't change.

### Open questions

Should every planned removal ship with this rehearsal as a standing test, run until the drop itself lands?

### Next step

Reuse the dependant-listing query for the next table retirement instead of trusting `cascade`.

Verified local evidence from a private codebase (names withheld per Master.md rule 12); PostgreSQL `pg_depend` and
`pg_policy` catalog documentation.

## DL-2026-10-01-02 — Aim the browser test at the server that is actually running

**Areas:** Software engineering; Tools and workflow

**Tags:** `testing`, `e2e`, `dev-environment`, `planning`

### What I learned

Before planning an end-to-end browser test, check which address and port the test runner
will target, and whether it starts its own server or reuses one that is already running.
If the runner's configuration points somewhere else, the plan quietly assumes a server
restart, and restarting shared local services can stop work that other sessions depend on.

### What I did

A UI change was planned with a browser test as its final check. The runner's configuration
expected a different port from the development server that was running, and its default
was to start a fresh server. Getting it to run would have meant restarting services another
part of the stack was using. The fix was to point the runner at the running server and let
it reuse it, and to make that check part of planning rather than discovering it at the end.

### Evidence or example

Read the runner's configured base URL and "reuse existing server" setting, then compare
them with the port of the server you will test against, before writing the test plan.

### Why it matters

A browser test that cannot reach the right server fails late, after the code is written,
and the obvious workaround (restart everything) can break shared local environments.

### Open questions

Should the runner's target be derived from the same configuration that starts the
development server, so the two can never disagree?

### Next step

Add "confirm the test runner's target and server reuse" to the planning checklist for any
change that ends with a browser test.

### Sources

Verified local evidence from a UI lane's review of its own browser-test step, 2026-10-01.
Lesson proposed by that lane and accepted by the project owner.
